The eight vitals

Eight checks on your token system

Each check is graded on its own, against evidence pulled from your repository. There is no single overall score, because averaging these would hide the one thing you need to see. If your system has no dark mode, that check is marked not applicable rather than counted against you. And if a check could not run at all, it says blocked instead of quietly passing.

Coverage

Orphans & enforcement

Tokens nothing uses, and what stops this coming back

Orphaned tokens make your system look bigger and more capable than it really is. They stick around because nothing breaks when they go, so nobody ever gets a reason to remove them.

Defined, but never used

0 of ~53 tokens · none found

Every declared token resolves to at least one real reference elsewhere in apps/v4. Two that looked orphaned on a first pass turned out not to be: --code-highlight/--code-number back the code-block syntax-highlighting rules inside globals.css itself (lines 365, 372, 426), and --selection/--selection-foreground back the global ::selection rule (globals.css:196) rather than any per-component class.

What is protecting this today

0 rules · 0 CI gates

No lint rule or CI gate in this repository reads the token layer. apps/v4/eslint.config.mjs is scoped to type-import style and React Hooks correctness; there is no stylelint config anywhere outside CLI test fixtures for other people's projects. .github/workflows/code-check.yml runs lint / format:check / typecheck, and validate-registries.yml checks registry namespace collisions — none of them look at a color, a spacing value, or a token reference.
Nothing here is protected from coming back. Every finding in this report could reappear tomorrow without anyone being told. The cheapest first move is a lint rule banning bracket-arbitrary literals that match an existing utility — that alone would have caught both redundant findings above.
